# OUxSBLI 向けマークダウン文書作成規則

この文書では、`architecture.md`、`context.md`、`technical_doc.md` の 3 つの異なるマークダウン文書ファイルを維持するための厳格な規則を定義します。各ファイルは、それぞれ特定の目的と対象読者を想定しています。

---

## 概要表

| 項目 | architecture.md | context.md | technical_doc.md |
|--------|-----------------|------------|------------------|
| **主な対象** | AIエージェント | AIエージェント | 人間の開発者 |
| **目的** | システム構造と設計 | 実装の詳細 | 技術リファレンス |
| **形式** | 簡潔で構造化 | 詳細かつ整理された | 文章＋図解 |
| **更新頻度** | アーキテクチャ変更時 | コード更新時 | メソッド変更時 |
| **関数の記載** | モジュール名のみ | はい、すべてのサブルーチン | はい、主要なもののみ |
| **物理モデルを含むか？** | いいえ | ほとんどない | はい、詳細 |
| **コード例？** | 擬似コードのみ | 実際のコードスニペット | 数式と概念 |

## 1. architecture.md - コンパクトでAI最適化された設計文書

### 1.1 目的
- **対象読者**: AIエージェント（Copilot、Claudeなど）
- **ユースケース**: AIが最小限のトークン数でシステム構造、ナビゲーション、設計パターンを理解できるようにする
- **目標**: 冗長な文章を使わずに、AIがモジュール間の関係を推論できるようにする

### 1.2 コンテンツ構成（必須セクション）

#### **1.2.1 トップレベルアーキテクチャ図** (必須)
- 3～5つの主要なレイヤーを視覚的に表現
- ASCIIアートまたはテキストベースのブロック図を使用
- データフローを示す: 入力 → 処理 → 出力
- **制約**: 図は最大20行

```
例:
┌───────────┐
│ 入力 Q    │
├───────────┤
│ フラックス│
│ 演算      │
├───────────┤
│ BC        │
│ 更新      │
├───────────┤
│出力 Q     │
└───────────┘
```

#### **1.2.2 モジュール依存関係グラフ** (必須)
- 各モジュールとその**直接的な依存関係のみ**を列挙してください
- 形式: `module_name: [dep1, dep2, dep3]`
- 推移的依存関係は記載しないでください
- リストは30モジュール以下に抑えてください

```
例:
calc_time_dev.f90: [calc_physical_quantities, calc_keep_kernel_internal, calc_visc2, set_bc_common]
calc_keep_kernel_internal.f90: [mod_constant, mod_globals]
calc_slau_kernel_internal.f90: [mod_constant, mod_globals, calc_muscl]
```

#### **1.2.3 モジュールカテゴリ（ティア分類）** (必須)
- ティア（1～7）ごとにグループ分けする
- 各モジュール：名前、ファイルパス、1行以内の簡単な目的
- **形式**: `Tier N: [モジュール名] (ファイルパス) - 目的`
- **制約**: モジュールあたり最大1～2行

```
例:
Tier 1: [mod_globals] (3D_solver/ETGV/mod_globals.f90) - 格子サイズおよびスキームパラメータ
Tier 1: [set] (3D_solver/ETGV/set.f90) - 格子初期化および境界条件の設定
Tier 3: [calc_keep_kernel_internal] (3D_solver/src/calc_keep_kernel_internal.f90) - 多精度 KEEP フラックスカーネル
```

#### **1.2.4 データ構造** (必須)
- **モジュール間で渡される主要なデータ構造のみ**を記載すること
- 形式: `名前(次元) : 型 : 説明`
- **制約**: 最大15個のデータ構造。AIが知る必要があるもののみ

```
例：
Q(5,nx,ny,nz) : real(8), device : 保存変数 [ρ, ρu, ρv, ρw, E]
E(5,nx-1,ny-2,nz-2) : real(8), device : x方向の対流フラックス
T(nx,ny,nz) : real(8), device : 温度場
detector(nx,ny,nz) : real(8), device : 衝撃波検出センサー
```

#### **1.2.5 設計パターン** (必須)
- 最大4つの主要パターン
- 各パターンについて：パターン名、2～3行の説明、1つの短いコード例

```
例：
**パターン：パラメータに基づく精度選択**
  kind(id_accuracy) を使用して、コンパイル時に2次/4次/6次を選択する。
  io = kind(id_accuracy) / 3 → ステンシルサイズとして0、1、または2

**パターン：共有メモリのタイリング**
  オーバーラップを伴うステンシルデータの読み込み、スレッドの同期、内部ループでのグローバルメモリの回避
  帯域幅を10～100倍削減
```

#### **1.2.6 実行フロー** (必須)
- 箇条書きを用いた単一タイムステップのシーケンス
- 主要なステップのみ6～10個を示す（サブステップは含めない）
- ステージ数と同期ポイントを記載

```
例：
1. [ステージ1] calc_physical_quantities(Q → T, μ)
2. [ステージ1] calc_keep_x_in, _y_in, _z_in (Q, T → E, F, G)
3. [ステージ1] calc_visc2 (Q, T, μ → ΔE, ΔF, ΔG)
4. [ステージ 1] 右辺の計算および Q の更新
5. [ステージ 1] set_bc_cyclic + MPI_exchange (非同期)
6. (RK スキーム用にステージ 2、3 を繰り返す)
```

### 1.3 architecture.md のスタイル規則

- **言語**: 英語、命令形（「Xを追加する」、「Yを計算する」）
- **冗長性**: 最小限に抑える - 概念ごとに1文
- **見出し**: #, ##, ### のみを使用（最大3階層）
- **リスト**: 箇条書き形式、詳細な説明は不要
- **コード**: 擬似コードのみ（実際のFortranではない） - 実装ではなく意図を示す
- **専門用語**: 使用可（GPU、共有メモリ、ステンシル、SLAU、KEEP）
- **行長**: 可能な限り100文字以内に収める
- **禁止**:
  - 長い文章の段落
  - 論文への言及
  - 詳細な物理方程式
  - 完全な関数シグネチャ
  - 歴史的背景

### 1.4 architecture.md のメンテナンス規則

- **更新のタイミング**:
  - 新しいモジュールの追加／削除
  - データ構造の変更
  - カーネルの名称変更またはリファクタリング
  - 実行フローの根本的な変更

- **更新対象外**:
  - バグ修正
  - パフォーマンスの微調整
  - 変数名の軽微な変更
  - ドキュメントの改善のみ

- **検証**: 要約版が印刷して2～3ページに収まるか？ 収まらない場合は、内容を削る。

## 2. context.md - AIエージェント向けの詳細な実装コンテキスト

### 2.1 目的
- **対象**: コードの深い理解タスクを行うAIエージェント（Copilot、Claude）
- **ユースケース**: AIは、各関数/サブルーチンが何を行うか、なぜ存在するか、そして物理モデルとどのように関連しているかについての詳細な知識を必要とする
- **目標**: AIが実装を修正、拡張、または説明するために十分なコンテキストを提供する

### 2.2 コンテンツ構成 (必須セクション)

#### **2.2.1 概要とプロジェクトの背景** (必須)
- 以下の内容を説明する3～4段落：
  - OUxSBLIとは何か、その目的
  - 主なユースケース（SBLI、TBLなど）
  - このアプローチを採用した理由（GPU、高次など）
- **目的**: AIが「ゲーム」を理解できるよう支援する

#### **2.2.2 科学的背景（概要）** (必須)
- 支配方程式: オイラー方程式／非保定形式のNS方程式
- 主要な物理現象: 衝撃波、境界層、乱流
- 重要性の説明: 最大1～2段落
- **不可**: 導出、高度な理論、研究論文

#### **2.2.3 モジュールごとの実装詳細** (必須)
**主要な各モジュール（計20～30個）について、以下を記載すること：**

```
### mod_globals (3D_solver/ETGV/mod_globals.f90)

**目的**：問題の設定を制御するシミュレーションパラメータを保持する

**主要パラメータ**：
- id_visc (整数)：2=ナビエ・ストークス、4=オイラー
- id_scheme (実数)：0=KEEP、2=SLAU、4=Roe
- id_accuracy (パラメータ): 2/4/8（2次/4次/6次精度）
- nx, ny, nz: 格子次元 (INTEGER, パラメータ)
- Lx, Ly, Lz: 領域サイズ (REAL(8), パラメータ)
- threadsE, threadsF, threadsG (type(dim3)): GPUスレッドブロック構成
- dt: 時間ステップ (REAL(8), パラメータ)

**主要な関数/サブルーチン**: なし (これはパラメータ専用モジュールです)

**依存関係**: cudafor のみ

**使用先**: すべてのシミュレーションモジュール (calc_time_dev, calc_keep_* など)

**使用例**:
  if (kind(id_accuracy) == 4) then
    ! 4次精度が選択された - 4点ステンシルを使用
  endif

**重要な注意事項**:
- 変更はコンパイル時のみ有効（再ビルドが必要）
- スレッドブロックの次元は、GPUおよび問題の規模に応じて調整する必要がある
- id_viscとスキームの不一致はアーティファクトを引き起こす可能性がある
```

**各モジュールに必要な項目：**
1. ファイルパス
2. 目的（1～2文）
3. 主要なパラメータ／変数（パラメータモジュールの場合）
4. 主要な関数／サブルーチン（名前＋サブルーチンごとの1行の説明）
5. 依存関係（直接的なもののみ）
6. 使用元（どの他のモジュールがこれを呼び出すか）
7. 使用例または擬似コードのスニペット
8. 実装上の注意点や落とし穴

#### **2.2.4 サブルーチンレベルの詳細**（モジュールあたり10以上のサブルーチンがある場合に必須）

サブルーチンが多いモジュールについては、以下のサブセクションを追加してください：

```
### calc_time_dev.f90 サブルーチン

**RungeKutta_3rd(id_RungeKutta, id_rescale, myrank, mygpu, nx, ny, nz, ...)**
- 目的：3段階TVD RK3時間ステップ法（低メモリ使用量版）
- 入力：Q(5,nx,ny,nz) 保存型状態、格子形状、メタデータ
- 出力: 3段階のRK計算により更新されたQ
- 主な手順:
  1. 3回繰り返す: calc_physical_quantities → calc_EFG → RHS → UpdateQ
  2. 段階1および2の後: 係数の簡約補間
  3. 段階3の後: TVD特性を保証した完全な更新
- 呼び出されるGPUカーネル: (名前、引数なし)
- MPI呼び出し: ゴースト領域の非同期送信/受信
- 備考: CFL ≤ 1.0 の場合常に安定; RK4 より精度が低い

**RungeKutta_4th(id_RungeKutta, id_rescale, myrank, mygpu, nx, ny, nz, ...)**
- 目的: 4段階の古典的RK4時間ステップ
- ... (同様の構造)
```

#### **2.2.5 データフロー図** (任意だが推奨)
- モジュール間のデータ移動を示すテキストベースの図
- 例: `Q → [calc_physical_quantities] → T, μ → [calc_keep_x_in] → E`
- 主要セクションごとに最大1～2つ

#### **2.2.6 統合例** (必須)
AIが呼び出し/変更方法を理解できるよう、「統合スニペット」を提供してください：

```
**統合例：新しい境界条件の追加**

1. 以下のサブルーチンを含む set_bc_mybc.f90 を作成する：
   - set_bc_mybc_init(nx, ny, nz, Q) : IC用のCPUバージョン
   - set_bc_mybc(myrank, nx, ny, nz, Jacobian, Q) : GPUカーネル

2. calc_time_dev.f90の各ステージの後に以下を追加します：
   call set_bc_mybc(myrank, nx, ny, nz, Jacobian, Q)

3. Makefileを更新し、set_bc_mybc.f90を含めるようにします

4. テスト：既存のテストケース（TGV）を実行し、Qの保存性を検証します
```

### 2.3 context.md のスタイル規則

- **言語**：英語、半技術的、AIに説明するような口調
- **詳細度**：中程度 - AIが理解できる程度の詳細さを保ちつつ、小説並みの長さにはしない
- **構成**：
  - 一貫したモジュールテンプレート（目的、入力、出力、手順、備考）
  - モジュールあたりサブルーチンが5つを超える場合は、サブセクションを設ける
  - 統合例はコードのようなテキストブロックとして記述
- **コード**:
  - サブルーチンのシグネチャには実際のFortranを使用
  - 論理フローには擬似コード/コメントを使用
  - 意図/型を含む完全な関数プロトタイプ
- **リスト**：箇条書きと構造化された表を併用
- **見出し**：#、##、###、####を使用（最大4階層）
- **参照**：「データ構造については architecture.md を参照」といった引用は可
- **物理的背景**：最小限に抑える - 導出ではなく実装に焦点を当てる
- **禁止事項**:
  - 長文の段落
  - 完全な導出や論文
  - 歴史的背景や変遷
  - パフォーマンス指標（technical_doc.mdを除く）
  - 人間による主観的な議論（例：「我々は…を発見した」）

### 2.4 context.mdの記述ルール

**必須記載事項:**
- 3D_solver/src/ 内の全モジュール（コアソルバー）
- ケース固有の set.f90 ファイル（ETGV、SBLI など、各ケースごと）
- すべての mod_globals.f90 パラメータセット
- すべての calc_*_kernel*.f90 ファイル

**推奨記載事項:**
- 主要な時間積分関数
- すべての対流/粘性スキームのベース
- 境界条件の実装

**任意:**
- ヘルパー関数（utility_sort、print_debug など）
- 自動生成ファイル
- 一時的なコードやデバッグ用コード

### 2.5 context.md のメンテナンス規則

- **更新のタイミング**:
  - 新しいサブルーチンが追加された場合
  - 関数のシグネチャが変更された場合（意図、型、次元）
  - サブルーチン内のアルゴリズムが大幅に変更された場合
  - 新しいモジュールが作成された場合

- **更新しない場合**:
  - 内部変数の名前変更
  - コメントのみの変更
  - 空白や書式設定
  - 軽微なロジックのリファクタリング（入出力の挙動が同じ場合）

- **検証**: AIがこのコードの呼び出し方や修正方法を理解できるか？ はい → OK。

## 3. technical_doc.md - 人間が読める技術リファレンス

### 3.1 目的
- **対象読者**: 人間の開発者（研究者、ポスドク、インターン）
- **利用ケース**: CFD手法、数値スキーム、パフォーマンスに関する考慮事項の理解
- **目標**：実装の意思決定やデバッグのための包括的な技術リファレンス

### 3.2 コンテンツ構成（必須セクション）

#### **3.2.1 プロジェクト概要**（必須）
- OUxSBLIとは（3～4段落）
- 主な機能とユースケース
- 対象読者およびスキルレベル
- **トーン**：専門的な研究

#### **3.2.2 計算の基礎**（必須）
- 保存則形式の支配方程式（オイラー、ナビエ・ストークス）
- 物理パラメータ（γ、R、Pr、Ma、Reなど）
- 初期条件・境界条件の種類
- **記載内容**：LaTeX方程式 （technical_docでのみ許可）

#### **3.2.3 空間離散化**（必須）
主要な各スキーム（KEEP、SLAU、Roeなど）について：

```
### 3.3.1 KEEP（運動エネルギーおよびエントロピー保存）スキーム

**数学的定式化**：
  対流フラックスをエネルギー保存形式に分解：
  E = E_adv + E_press（ここで E_adv は運動エネルギー不変量を保存する）

**精度**：2次、4次、6次の有限差分オプション

**実装ファイル**：
  - calc_keep_3d.f90：フラックス関数 KEEP2、KEEP4、KEEP6
  - calc_keep_kernel_internal.f90: GPUカーネル calc_keep_x_in など

**精度特性**:
  - 滑らかな流れにおいて次数 p で収束する (p=2,4,6)
  - 非粘性流において運動エネルギー不変性を維持する (テスト: TGV)
  - 滑らかな格子上で明示的な散逸項なしでも安定

**性能特性**:
  - フロップス/点: ~200 (2次) ～ ~400 (6次)
  - メモリ帯域幅: RTX 4090で通常 ~100 GB/s
  - 2次法に対する速度向上率: 0.8倍 (計算コストが高く、時間ステップを大きくすることで相殺される)

**使用場面**:
  - 非粘性流れ（TGV、IVST）
  - 滑らかな乱流のDNS/LES
  - スキーム特性に関する研究

**注意点**:
  - 各境界に (io+1) 個のガードポイントが必要
  - センサーがない場合、衝撃波付近で散逸的になる可能性がある
  [実装の詳細については context.md を参照]
```

#### **3.2.4 時間離散化** (必須)
- RK3-TVD: 安定性、CFL限界、TVDの証明
- RK4: 古典的な定式化、安定領域、CFL ~0.8
- 再スケーリング変種: SBLIにおける目的

#### **3.2.5 GPU実装の詳細** (必須)
- スレッド構成 (1D、2D、3D ブロック)
- 共有メモリ戦略 (パディング、バンク競合)
- グローバルメモリアクセスパターン (コアリシング、ストライド)
- コードスニペット付き最適化手法の例

#### **3.2.6 MPI 並列化** (必須)
- ドメイン分解戦略
- スキーム/精度ごとのゴースト領域サイズ
- 同期ポイント
- スケーリングの限界と負荷不均衡に関する懸念

#### **3.2.7 収束性に関する検討** (必須)
- 格子収束率（グラフ、表）
- 精度と格子細分化の関係
- 例：TGV運動エネルギー減衰率

#### **3.2.8 パフォーマンスプロファイリングと最適化** (必須)
- 代表的な測定値（FLOP数、メモリ帯域幅、レイテンシ）
- nsys、ncuコマンドを用いたプロファイリング
- 一般的なボトルネック
- 事例研究：最適化による速度向上

#### **3.2.9 デバッグとトラブルシューティング** (必須)
- よくあるエラーメッセージと対処法
- 検証テスト（TGVエネルギー、衝撃センサーの出力）
- メモリの問題（GPU RAM不足、メモリ割り当て）
- MPI通信のデッドロック

#### **3.2.10 付録** (任意)
- 用語集
- 数学記号の定義
- 物理定数の値
- Fortran構文リファレンス

### 3.3 technical_doc.mdのスタイル規則

- **言語**: 英語、技術的、当該分野の専門家向けに記述
- **詳細度**: 完全に理解するために必要な範囲で詳細に記述
- **トーン**: 客観的、教育的、研究レベル
- **構成**:
  - 説明を伴う文章
  - 根拠を明記した数式
  - 主要なアルゴリズムのコードスニペット
  - 図・図表（ドキュメント内はASCII、必要に応じて外部リソースを参照）
- **数式**:
  - LaTeXの使用可: `$E = mc^2$` または `$$\frac{\partial Q}{\partial t} = ...$$`
  - すべての記号は使用前に定義すること
  - 既知の結果を使用する場合は参考文献を引用すること
- **コード**:
  - アルゴリズムの説明には実働するFortranコードを使用
  - 高レベルなロジックには擬似コードを使用
  - 付随する説明を含めること
- **参考文献**:
  - 数学的スキームについては論文を引用すること
  - 実装の詳細については context.md を参照すること
  - システム構造については architecture.md を参照すること
- **見出し**: 必要に応じて #, ##, ###, #### を使用すること (階層レベル4)
- **表**: 結果、比較、スキームの特性に使用
- **図**: インラインのASCII図、サブディレクトリ内の外部画像ファイルを参照
- **許可される内容**:
  - 詳細な物理的説明と導出
  - 歴史的背景と変遷
  - 著者の考察（「このアプローチは…であるため、XYZを回避できる」）
  - 性能比較
  - 研究上の知見

### 3.4 technical_doc.md の記載範囲に関するルール

**必須項目:**
- 完全な数学的定式化
- 主要なすべてのスキーム（KEEP、SLAU、Roe など）
- 時間・空間離散化理論
- GPU/MPI アルゴリズムの詳細
- 収束性と誤差解析

**推奨事項：**
- デバッグ手順
- 性能ベンチマーク
- 検証用テストケース
- 最適化手法

**任意：**
- 詳細な証明（代わりに論文を引用すること）
- 広範なコードリスト（重要なスニペットのみを表示）
- 広範な結果表

### 3.5 technical_doc.md のメンテナンス規則

- **更新すべき場合**:
  - 新しい空間/時間スキームが追加された
  - 性能特性が大幅に変化した
  - 数学的定式化が修正された
  - 誤差解析または収束率が変化した
  - デバッグ手順が発見/改良された

- **更新しない場合**:
  - 内部実装のリファクタリング（外部インターフェースに変更がない限り）
  - コードのロジックに関する説明のみ（その場合は context.md を更新）
  - 軽微な誤字の修正

- **妥当性確認**：研究者が数学を理解し、実装を検証できるか？ はい → OK。

## 4. 相互参照のルール

### 4.1 ドキュメント間のリンク

**architecture.md からのリンク：**
- 「実装の詳細については context.md を参照」
- 「理論については technical_doc.md のセクション X.X を参照」

**context.md からの引用:**
- 「アーキテクチャの概要については architecture.md を参照」
- 「数学的な詳細については technical_doc.md のセクション X を参照」
- 「API シグネチャについては api.md を参照」

**technical_doc.md からの引用:**
- 「実装については context.md のモジュールセクションを参照」
- 「システム構造については architecture.md を参照」
- 「完全な API シグネチャについては api.md を参照」

### 4.2 重複の回避

| 内容 | 参照先 | 理由 |
|---------|---------|-----|
| 数学的導出 | technical_doc.md | 人間には必要だが、AIには不要 |
| モジュールの依存関係 | architecture.md | 簡潔で、AIが必要とする |
| 関数のシグネチャ | context.md + api.md | 両方ではなく、api.mdは自動生成 |
| 実装の詳細 | context.md | AIがコードを理解する必要がある |
| パフォーマンス指標 | technical_doc.md | 人間が解釈・議論する |
| 実行フロー | architecture.md | AIには簡潔な形式が必要 |

## 5. 更新ワークフロー

### 5.1 コード変更時

1. **コード変更**: Fortranファイルを修正
2. **architecture.mdを更新するか？**
   - モジュールの追加/削除があった場合: はい
   - 実行フローが変更された場合: はい
   - それ以外の場合：NO
3. **context.md を更新するか？**
   - サブルーチンのシグネチャが変更された場合：YES
   - 主要なロジックが変更された場合：YES
   - 新しい関数が追加された場合：YES
   - それ以外の場合：NO
4. **technical_doc.md を更新するか？**
   - アルゴリズム/スキームが変更された場合：YES
   - パフォーマンスへの影響が著しい場合：YES
   - それ以外の場合：NO
5. **api.mdを更新する？** 自動生成 - システムが対応している場合はスクリプトを実行

### 5.2 更新頻度の目標

- **architecture.md**：年1～2回（大規模なリファクタリング時）
- **context.md**：年4～8回（コード変更、新機能追加時）
- **technical_doc.md**: 年2～4回（アルゴリズムの更新時）
- **api.md**: リリースごとまたは毎月（自動生成）

**シナリオ**: 新しいスキーム `calc_wenofv_kernel_internal.f90` を追加

### architecture.md への追加:
```
Tier 3: [calc_wenofv_kernel_internal] (3D_solver/src/calc_wenofv_kernel_internal.f90) - 5次WENO有限体積法
  依存関係: [mod_constant, calc_weno_3d]
  カーネル: calc_wenofv_x_in, calc_wenofv_y_in, calc_wenofv_z_in
```

### context.md 追加:
```
### calc_wenofv_kernel_internal.f90

**目的**: 高精度な衝撃波捕捉のためのWENO有限体積法を実装する

**主要な関数/サブルーチン**:
- calc_wenofv_x_in(nx, ny, nz, Q, sensor, E): x方向のWENO-FVカーネル
- calc_wenofv_y_in(nx, ny, nz, Q, sensor, F): y方向のWENO-FVカーネル
- calc_wenofv_z_in(nx, ny, nz, Q, sensor, G): z方向のWENO-FVカーネル

**依存関係**: mod_constant (γ, R, など), calc_weno_3d (フラックス関数)

**使用先**: calc_flux_base.f90 (ディスパッチャ)

**実装に関する注記**:
- WENO-5 (5点ステンシル、滑らかな領域で5次)
- 衝撃波を自動検出し、局所的に次数を低減
- 共有メモリ: ステンシルデータ + WENO重みバッファ
```

### technical_doc.md 追加:
```
### 3.3.X WENO 有限体積法

**動機**: KEEP/SLAUは精度または安定性を提供するが、WENOは両方を兼ね備える

**数学的基礎**:
複数の3点サブステンシルを用いた、重み付けされた本質的に非振動的な再構成...
[式はここに]

**実装**:
GPUカーネルがセルごとに適応重みを計算し、その後、左/右端の値を再構成する...

**性能**:
- RTX 4090: ~150 GFLOP/s (KEEP/SLAUよりも計算負荷が大きい)
- 5点ステンシルが必要（ガードゾーンは片側あたり2つ以上必須）
- CFL ≤ 0.8 を推奨（Roeと同様、KEEPより安定性は低い）

**使用すべき場合**：強い衝撃波を伴う極超音速流；処理速度は遅いが堅牢性が高い
```
